# Лабораторна робота 3 - варіант 8


### Частина 1 - клас `Рядок`

Створено чотири початкові рядки. Для кожного доступні всі операції варіанта 8:

- пошук заданого символу;
- розворот рядка;
- додавання нового тексту;
- виведення значення й довжини.

Меню окремо зберігає масив `LaboratoryString[]`, відновлює його в новий масив і серіалізує колекцію рядків. Формат та шлях до файлу обирає користувач.

Після десеріалізації значення й довжини рядків однакові в обох випадках. Відмінність структурна: масив має фіксовану довжину, а `List<LaboratoryString>` можна доповнювати або скорочувати без створення нового контейнера.

### Частина 2 - студенти та додаткові сутності

Для студента є прізвище, ім'я, курс, номер студентського квитка й дата народження у форматі `дд.ММ.рррр`. Реалізовано додавання, пошук, видалення, збереження і читання з файла. Окрема операція рахує студентів **4-го курсу, які народилися навесні**, після завантаження даних з обраного файлу.

Також реалізовані додаткові сутності варіанта 8 - `Baker` і `Entrepreneur` - з власними меню, CRUD-операціями, збереженням/читанням та вмінням «стрибати з парашутом».

## Архітектура

```text
Lab3.App              точка входу: Program.Main() -> Menu.MainMenu()
        |
Lab3.Presentation     PL: Menu, консоль, моделі введення
        |
Lab3.Business         BLL: EntityService, перевірки, власні моделі та винятки
        |
Lab3.Data             DAL: EntityContext, DAL-сутності, DataProvider-и, файли
```

`StudentEntity`, `BakerEntity`, `EntrepreneurEntity` і `StringEntity` існують тільки в DAL. У BLL та PL застосовані окремі моделі, а конвертація виконується в `EntityService`. Отже, рівні не передають один одному DAL-сутності.

`EntityService` не містить `Console`, `Stream`, `File` або іншого прямого доступу до файлів. Файл створює тільки `EntityContext` через абстракцію `DataProvider`.

`EntityContext` має узагальнені операції повного життєвого циклу файла: `Create<T>`, `Open<T>`, `Update<T>`, `Close` та `Delete`. Потоки відкриваються тільки всередині провайдерів через `using`, тому після кожної операції фізичний потік гарантовано закритий; `Close` завершує логічне відстеження файла контекстом. У головному меню пункт **«Операції з файлами»** дозволяє явно створити порожній файл або видалити його.

## Формати серіалізації

У меню можна обрати один із чотирьох форматів і ввести повне ім'я файлу:

1. `BinaryDataProvider` - справжній двійковий запис полів через `BinaryWriter` із заголовком і перевіркою структури;
2. `XmlDataProvider` - `XmlSerializer`;
3. `JsonDataProvider` - `System.Text.Json`;
4. `CustomDataProvider` - власний текстовий формат: заголовок полів і Base64-подання кожного значення.

`BinaryFormatter` навмисно не використовується: у сучасному .NET він небезпечний і вимкнений. Бінарний провайдер створює та читає контрольований власний двійковий формат через `BinaryWriter`/`BinaryReader`.

## Запуск

```bash
cd Lab_3
dotnet build Lab_3.slnx
dotnet run --project Lab3.App
```


1. `Lab3.App/Program.cs`: у `Main()` лише виклик `Menu.MainMenu()`.
2. Залежності проєктів: `App -> Presentation -> Business -> Data`.
3. `EntityService`: не працює з консоллю та файлами; помилки зберігання перетворює на власний `StorageOperationException`.
4. `EntityContext` і чотири похідні від `DataProvider`.
5. Збереження рядків як масиву та як колекції у різних форматах, після чого відновлення даних.
6. Завантаження студентів із файла й обчислення кількості студентів 4-го курсу, народжених у березні-травні.
